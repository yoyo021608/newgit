设计文档

一、业务理解

1.这个项目是做什么的？

学长给的题目是“个人知识库管理”，核心问题我理解是：用户收藏了很多文档、笔记，以及自己整理了很多笔记，但信息越攒越多，没法直接找到并且使用。用户需要的不是“存东西”的工具，而是“问东西”的工具，是随手丢进去，用一句话就能问出来的工具，而且知道答案来自哪里。

2.我的解决方案是什么？

我做的不是一个文档管理系统，而是一个“能基于文档内容回答问题的 AI 助手”。用户上传文档，系统读取内容、建立索引，用户提问时系统从文档里检索相关内容，AI 生成回答，并且对于文档里面比较模糊或者不太清楚的问题，可以进行补充回答，同时显示答案来源。

为什么选这道题？

三道题里我选了这道，因为我在准备进实验室的时候还没有拿到项目主题，所以看黑马自学了 FastAPI ， MySQL，linux等等，刚好很多知识吻合这个项目，再加上也了解一些 RAG 的概念，在这个方向上我能做得更深。

二、设计深度的体现

这个项目里我重点做了几个方面来体现设计深度，不只是把功能跑通，而是去思考怎么做的更好，怎么样更符合人类使用习惯。

1. 混合检索：精确匹配 + 向量检索

大部分 RAG 项目只做向量检索，但我发现一个问题：用户问“介绍一下语文”时，向量检索能返回相关内容，但用户问“语文、数学、英语”时，向量检索会漏掉部分文档，并且漏掉的不是固定的。说明这些文档是正常入库的，只是没匹配到，所以我加了精确匹配，先按文档名去找，再走向量检索，两者结合。这样用户指定要查哪个文档时能准确定位，模糊搜索时又能靠向量检索兜底。

2. 多步检索工作流

第一次检索结果不足时，系统自动改写问题再查一次。这个设计解决了“文档内容太短、向量检索相似度不够”的问题。比如用户上传了一份只有一句话的文档，问一个稍微宽泛的问题，向量检索可能找不到，但改写问题后扩大了检索范围，就能把相关内容找回来。

3. 工具调用和技能调用的统一入口

用户的问题可能分为几类：查文档内容、查天气、翻译、计算。如果让用户自己去判断这个问题该用哪个功能，体验很差。我做了一个统一入口，前端先尝试快速接口，系统自动判断是走工具调用、技能调用还是 RAG 检索，用户不需要知道背后的逻辑。

4. 流式和非流式的区分

一开始我想都使用流式，因为在我接触的ai里面，问答都是流式，且可以减少等待焦虑，但是我测试时发现，工具调用用流式会导致光标一直闪、内容出不来，用户体验反而更差，工具调用和技能调用响应快，所以我走非流式一次性返回；RAG 问答响应慢，我走流式逐字输出。

5. 关键词过滤

多步检索扩大了召回范围，但也会混入不相关内容。我加了关键词过滤，只保留文件名或内容包含问题关键词的文档，在召回率和准确率之间做了平衡。


三、架构设计

系统怎么分层？

我分了四层：

路由层（routers/）——接收请求、参数校验、返回响应
业务层（routers/ 中实现）——核心业务逻辑，比如检索、问答
数据层（crud/）——数据库操作，增删改查
模型层（models/）——定义数据表结构

为什么这样分？

这个分层思维是从网课里面学习到的，这样做主要是为了职责清晰。路由层只管接收请求，数据层只管操作数据库，不会出现路由层直接写 SQL 的情况。这样改一层不影响其他层，比如以后要从 MySQL 换成 PostgreSQL，只需要改数据层。另外每层可以单独测试，方便排查问题。


四、技术选型

为什么用 FastAPI？

最直接的原因就是我学习的网课老师推荐使用fatapi，因为 FastAPI 自带参数校验、自动生成 API 文档，性能也更好。我需要快速搭接口，同时要有清晰的文档可以看，FastAPI 的 Swagger 文档正好满足这个需求。

为什么用 SQLAlchemy？

最直接的原因依旧是因为网课老师推荐，并且SQLAlchemy 是 Python 最流行的 ORM，用它可以不用手写 SQL，代码更清晰。而且它支持多种数据库，以后要换数据库也方便。

为什么用 ChromaDB？

ChromaDB 是轻量级的向量数据库，本地部署就行，不需要额外服务器。我只存文档向量，数据量不大，用 ChromaDB 够了。以后数据量大了可以换 Milvus 或 Pinecone。

为什么用通义千问？

我对比了 OpenAI。OpenAI 效果更好，但国内访问不稳定，需要翻墙。通义千问国内可以直接用，中文效果不错，而且有免费额度。我选了通义千问作为主力，同时代码里保留了多模型切换的能力。

为什么用 Docker？

学长要求里写了“能用 docker-compose 部署运行”。Docker 化之后，学长拿到项目只需要执行 docker-compose up -d，就能把后端、MySQL、Redis 全部跑起来，不需要装 Python、MySQL、Redis，也不用配环境变量。


五、开发中做的重要决策

1. 重排序功能本来想加上去，后面决定跳过了

我计划用 cross-encoder 模型对检索结果重新排序，提高相关性。但模型要从 Hugging Face 下载，网络一直不通，换镜像源、手动下载都试了，还是不行。

2. 工具调用走非流式，RAG 走流式

测试时发现，问“翻译一下 hello world”时，技能调用响应很快，但用流式传输反而导致前端卡顿，光标一直闪但不出结果。我做了区分：工具调用和技能调用走非流式接口，一次性返回完整结果；RAG 问答响应慢，走流式接口逐字输出，让用户知道“正在生成”。这样快速响应的功能不卡顿，慢速响应的功能保持流式体验。

3. 多关键词优先精确匹配文档名

向量检索在多关键词场景下有问题，用户问“语文、数学、英语”时，系统只返回部分文档。我改成先提取关键词，按文档名精确匹配，确保每个关键词都能找到对应的文档。没匹配到的再走向量检索兜底。这样既保证准确性又保证召回率。

4. 多步检索 + 关键词过滤

多步检索触发后，改写问题会扩大检索范围，但也会混入不相关的文档。比如问“人工智能是什么”，第二步检索把语文、数学、英语都带出来了。我加了关键词过滤，只保留文件名或内容包含问题关键词的文档，过滤掉无关内容。


六、设计文档必答

1. 知识怎么建模和组织？

知识通过文档表和文件存储来组织。用户上传的文档保存在 uploads/ 目录，数据库记录文件名、路径、类型、上传用户和时间。

我设计了三层检索链路，按顺序执行：

第一步：精确匹配文档名。从用户问题里提取关键词，去匹配已上传的文档名。如果匹配到了，说明用户可能明确指向了某个文档，直接读取该文档内容进入问答流程。
第二步：向量检索。如果文档名匹配不到，就把用户问题向量化，去 ChromaDB 里找语义相似的内容。这一步解决的是“问法灵活”的问题——用户可能问“唐宋八大家”，文件名是“中国古代文学史”，但内容里有相关描述，向量检索能找到。
第三步：多步检索。如果前两步都没找到，自动改写用户问题再查一次，作为兜底召回。
遇到的问题：

一开始我只用向量检索，测试时发现一个奇怪的现象。我上传了语文、数学、英语、物理、化学五份文档，问“帮我介绍一下语文、数学、英语”，系统只返回了语文和数学，英语被漏掉了。但单独问“介绍一下英语”时，又能准确找到。说明向量检索同时处理多个关键词时，结果会互相干扰。更奇怪的是，问“介绍一下语文”时，回答里却引用了数学和化学的文档。虽然语文排在最前面，但其他不相关的文档也被带了出来。

我改成先精确匹配文档名，再走向量检索。问“语文、数学、英语”时，先按文档名去找，确保每个关键词都能匹配到对应的文档。没匹配到的再走向量检索兜底。这样解决了多文档召回不全和引用不相关的问题。

2. 检索链路怎么设计？

检索链路：用户提问 → 提取关键词 → 精确匹配文档名 → 向量检索 → 混合检索（BM25 + 向量） → 取前3个结果 → LLM 生成回答。

检索不准我做了两件事：一是多步检索工作流，第一次检索结果少于2个时自动改写问题再查一次；二是明确告诉用户“未找到相关内容”，不编造答案。

遇到的问题：

多步检索触发后，出现了另一个问题。我上传了一份只有一句话的文档“人工智能是计算机科学的一个分支”，问“人工智能是什么”。第一次检索结果不足，触发了第二步，改写问题为“关于人工智能的相关内容”。第二步确实检索到了内容，但同时也把语文、数学、英语、物理、化学的文档都带出来了。回答里变成了“语文是...数学是...化学是...”，核心信息反而被淹没了。

我试了两种方案。一种是只取最相关的一个文档，回答很精准，但会丢失其他有价值的信息。另一种是修改 Prompt，让 LLM 优先使用最相关的文档。我选了第二种，因为用户可能同时问多个科目，保留其他文档作为补充还是有意义的。

3. Agent 怎么处理“一步答不好”的问题？

多步检索工作流是这样设计的：先用原问题检索，如果结果少于2个，自动改写问题再查一次，最后把两次结果合并去重。

遇到的问题：

除了上面提到的“改写后混入无关文档”的问题，还有一个困扰我很长时间的 bug。问“翻译一下 hello world”时，终端显示技能调用成功了，但前端一直卡着，光标闪烁但不出结果。最开始我试着刷新，退出后再进去，发现结果出来了，但是后面又不行了，答案出不来，后来发现是前端处理流式响应的方式有问题，工具调用响应很快，流式传输反而增加了前端渲染开销，导致卡顿。

我做了区分：工具调用和技能调用走非流式接口，一次性返回完整结果；RAG 问答走流式接口，逐字输出。

4. 怎么评估检索质量？

目前靠用户反馈来判断，回答底部会显示来源文档，用户能看出来答案是不是真的来自文档。

遇到的问题：

早期测试时发现，系统回答的内容有时候不是来自文档，而是模型自己编的。比如问“勾股定理是什么”，我没上传任何相关文档，但系统还是给出了回答，而且来源里显示了一个不相关的文档名。说明系统在文档里找不到内容时，模型用自己的知识编了答案，然后强行配了一个来源。

我加了“答案溯源”功能，回答时强制显示来源文档名。如果文档里找不到相关内容，系统会明确说“未找到相关内容”，而不是编答案。


七、其他遇到的问题

光标闪烁问题：流式输出结束后光标没有自动消失，一直在闪。我在前端加了移除光标的逻辑，回答完成后手动移除。

历史记录保存问题：考虑到正式的系统账户会有历史记录保存，所以我也加上了，用户使用更加方便，但是在开发后期，发现工具调用和技能调用走快速接口后，历史记录没有保存。我在快速接口里加了保存历史记录的逻辑，确保所有问答都能保存。

Docker 端口冲突：部署时 3306 端口被本地 MySQL 占用。我把 docker-compose.yml 里的端口映射改成了 3307:3306，让 Docker MySQL 用 3307 端口。
